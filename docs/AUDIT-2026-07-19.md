## Audit round — 2026-07-23 (v0.1.9.3: direct-play re-probe for null-codec media)

Bug: a category's videos wouldn't play — server logged 206 + "stream closed
prematurely" (benign Fastify client-abort) as the LAST line. Root cause: a
folder scanned before ffprobe was available stores NULL codecs; `canDirectPlay`
FAILS OPEN on unknown codecs, so an undecodable file (HEVC / 10-bit H.264 in an
mp4 container) is served as direct play (206) and the browser silently aborts.
Fix: `resolvePlayback` re-probes never-probed rows (`probed_at IS NULL`) at play
time, persists codec + pix_fmt + probed_at, and decides from real data (codec
name AND bit depth via `isBrowserSafePixFmt`); falls back to the optimistic
guess only when ffprobe is truly absent (logged). New `pix_fmt`/`probed_at`
columns. Client `<video> onError` now surfaces the previously-silent decode
failure.

R1 (adversarial): FAIL → fixed. Critical: pix_fmt was computed but NOT persisted
— the 10-bit gate worked once then regressed, and never ran for normally-scanned
files. Plus an infinite-reprobe footgun for stream-less files and the same
fail-open in the guest + federation start paths. Fixed by persisting pix_fmt +
a `probed_at` latch and sharing the decision (resolvePlayback) across all three
start routes.

R2 (fix-the-fix): FAIL → fixed. Critical: `playback.ts` getMediaById's explicit
column SELECT dropped the new columns (only federation's was updated) — so the
main + guest routes saw `probed_at === undefined` (== null) and reprobed every
play AND fell open on a probed 10-bit file when ffprobe was down. Fixed +
hardened: both getMediaById now `SELECT *` (matching getMediaItem) so a stale
column list can't silently drop a field. Re-verdict: PASS.

Verified live on the compiled build with the definitive latch sequence: good

mode=transcode with ZERO reprobe attempts (stored pix_fmt used, probed_at

## Audit round — 2026-07-23 (v0.1.9.4: auto-transcode fallback on direct-play failure)

Follow-up to v0.1.9.3: on the user's box FFmpeg was reachable (NVENC detected,
no `[preflight]` warning) yet a video still failed — a codec that PASSES the
direct-play whitelist but the browser can't decode (AV1 without browser support,
8-bit 4:2:2/4:4:4 H.264). Rather than keep enumerating codecs server-side (a
losing game — the browser is the authority), the player now REACTS: on a
direct-play decode error (`<video>` onError, mode='direct', error code 3/4) it
retries once with `force_transcode`, which the server honors
(`direct = decision.direct && !force_transcode`) → HLS transcode → plays.
Federated playback can't force through the proxy, so it goes straight to the
error. This is the 3-strike "different route": stop predicting compatibility,
observe the actual decode result.

R1 (adversarial): PASS with 1 Warning. State machine verified loop-proof (post-
retry mode='transcode' so onError's `mode!=='direct'` guard blocks re-entry;
forceTranscodeRef flips synchronously before the nonce bump; reset effect
declared before init so mediaId-change resets first, retryNonce-bump doesn't;
session torn down before re-init). Warning: a sub-360p source → getAvailableProfiles
returned [] → empty master playlist → generic error. Fixed: profiles floor to
the lowest rung (360p) when a known-dims source is below it (a latent bug on the
normal transcode path too). Also added the missing no-HLS-support else branch
(silent forever-loading → clear error).

R2 (fix-the-fix): PASS. getAvailableProfiles change is surgical (only known-dims
<360 flips []→[360p]; callers use it only when direct===false, so no
direct-decision flip; upscale-with-pad is valid). The onError-less-branch is
reachable only when no playback path matched. No regression.

Verified live: force_transcode start on a direct-playable H.264/AAC file →
mode=transcode (override works); normal start → direct. Tests 375→376.

### `:latest` was unguarded in four independent directions

All four verified against `docker/metadata-action` v5.10.0 source at the pinned
SHA, not inferred from docs:

1. `procRaw` has **no ref guard**, so `workflow_dispatch` from a branch published
   that branch as `:latest` — and as the ONLY tag, since every tag-scoped rule
   no-ops off a tag.
2. `procRefTag` passes `latest=true` for any tag with no pre-release check, and
   `Meta.setVersion` **latches first-write-never-demoted**, so an `-rc` tag took
   `:latest` even though `procSemver` computed `false`. Rule ORDER defeated the
   action's own pre-release protection.
3. No highest-tag comparison, so a hotfix off an older line moved `:latest`
   backward and silently downgraded everyone.
4. No concurrency group — two tag pushes race, last writer wins.

Fixes: job-level `if: startsWith(github.ref, 'refs/tags/v')`, `flavor: latest=false`
plus one gated raw rule, a `sort -V` newest-tag step, and a concurrency group with
`cancel-in-progress: false`. `latest=auto` reads like a safety feature and is not
one: it is per-rule, order-sensitive, and blind to the rest of the repo.

### Two regressions this round introduced and then fixed

- **Healthcheck**: retargeting to `/api/info` was right; tightening the predicate
  to `r.ok` was not. `/api/info` is not in the data-plane allowlist and the limiter
  keys on `req.ip`, so a 429 marked a live container unhealthy. Reverted to
  `<500` — a liveness probe asks "is the process serving?".
- **`parseTrustProxy`** reintroduced the exact exit-0 boot brick its own docblock
  claimed to prevent, two ways: it validated the _cleaned_ entry list but returned
  the _raw_ string (so `"127.0.0.1,"` threw inside Fastify), and it bounded the CIDR
  prefix high-only while proxy-addr throws on `range <= 0` (so `0.0.0.0/0` threw).
  Root cause of the miss was test shape — see the lesson below.

### Lessons

- **Assert against the real consumer, not the return value.** The trustProxy tests
  asserted what `parseTrustProxy` _returned_, which structurally cannot catch a
  value that passes validation and then throws downstream. Replaced with a property
  test: `Fastify({trustProxy: parseTrustProxy(x)})` must not throw for ANY x. It
  reproduced all 8 failing inputs immediately.
- **A green test that doesn't exercise the documented path proves nothing about it.**
  The CI `image` job boots the container with no volume, so it passes while the
  documented `docker compose up -d --build` is broken (see F1 below).
- **GHA cache is ref-scoped.** A tag-only workflow's `cache-from` can never hit,
  while `cache-to,mode=max` burns the repo's shared 10GB budget. Moved to `ci.yml`,
  writing only on master pushes.
- **`sbom: true` is not free.** It resolves BuildKit's scanner image by mutable tag,
  smuggling an unpinned upstream into the one job holding `packages: write`. Pinned
  the generator by digest via `attests:`.
- **Verify subagent findings against upstream source.** Every load-bearing claim was
  re-checked; one schema validator "failed" both workflows including the
  green-in-production `ci.yml`, which exposed a harness bug (PyYAML parses `on:` as
  boolean `True` under YAML 1.1), not a defect.

## Audit round — 2026-07-25 (v0.1.9.5: the CI hang, diagnosed rather than guessed)

No product code changed. This round exists because the previous one's fix for F7
was wrong in an instructive way, and the correction is worth recording.

### Three hangs, and two false conclusions drawn from them

The `Typecheck & test` job hung three times in about two hours, on three
different branches (`30162027944` Dependabot, `30163412400` a feature branch,
`30164977441` master). Two conclusions stated during the first two occurrences
were both wrong:

1. **"Force-cancelling destroyed the logs."** Wrong cause. `30162027944` was
   never touched by anyone and its logs are also `BlobNotFound`. The rule is
   simply that **a job ending `cancelled` uploads no logs at all**. Force-cancel
   was incidental.
2. **"The 15-minute guard fires late."** It does not. Both untouched hangs ran
   **20m01s to the second**: `timeout-minutes: 15` fires exactly on time, and
   GitHub then allows a **5-minute cancellation grace** before hard-killing. The
   extra five minutes is not a late timer — it is the runner waiting on a process
   that ignores termination. That reframes the whole diagnosis: a leaked timer
   dies on SIGTERM; this does not.

### Why the first fix could never have worked

v0.1.9.4's response to F7 was vitest `testTimeout`/`hookTimeout`/`teardownTimeout`
plus the `hanging-process` reporter. The timeouts were correctly identified as
non-causal at the time (they were already in force as defaults when the hangs
happened, so raising them fixes nothing) and were pinned only to freeze the
defaults. The reporter, however, wrote its handle dump to a log that the
cancellation then discarded — **instrumentation on a channel that the failure
mode destroys**. It shipped with an honest caveat that it was unverified; the
caveat turned out to be the important part.

### The mechanism, reproduced locally

Two things had to be true for the step to hang, and only one of them is
`timeout`'s job:

- A step stays alive while **any descendant holds its stdout pipe**. A wedged
  ffmpeg outliving node keeps the runner reading an open pipe long after the test
  process is gone. Reproduced: a fake suite that exits 0 while leaking a
  SIGTERM-ignoring grandchild hangs a pipe reader **indefinitely** (killed at 2
  minutes); redirecting the same suite's output to a file completes in **0s** with
  all output preserved.
- `timeout` alone does not fix that. On coreutils 9.4 a grandchild that ignores
  SIGTERM **survives**, and `timeout` still exits **124** because its direct child
  died — so `--kill-after` never reaches the survivor.

### The fix

`ci.yml`'s Test step now runs `timeout --kill-after=60s 300 npm test

> test-output.log 2>&1`, then cats the log and reaps stray `ffmpeg`/`ffprobe` by
exact name (`pkill -x`, which cannot match the step script the way `pkill -f`would). The step fails with 124 or 137 instead of the job being cancelled, so the
logs — including any`hanging-process` dump — actually upload. 137 versus 124
> also discriminates "ignored SIGTERM" from "merely slow", verified locally.

This is diagnostic, not curative: it does not stop the hang, it makes the next
one readable. The underlying wedge is still unidentified.

### Lessons

- **Instrumentation must survive the failure it instruments.** Ask what state the
  system is in when the evidence is read, not just when it is written.
- **A timestamp is not a measurement until you know what the clock includes.**
  "20 minutes on a 15-minute timeout" reads as a broken guard until you account
  for the grace period; the same number then becomes the strongest evidence for
  the actual cause.
- **`timeout` bounds a process, not a process tree.** Exit 124 means "my child
  died", not "the work stopped".

## Audit round — 2026-07-27 (base image: a shipped optimization that was inert in the artifact)

**v0.1.4's CPU fix never applied in the published container.** That round added
`-readrate 1.5` + `-readrate_initial_burst 120`, correctly feature-detected
because passing an unknown option makes ffmpeg exit fatally. The runtime stage
was `node:22-bookworm-slim`, whose newest ffmpeg is **5.1**, and
`readrate_initial_burst` needs **>= 6.1**. So the detection did its job, silently
chose the degraded path, and every user of every published image has paid the
un-burst start cost since 2026-07-20.

Verified at the binary rather than from version arithmetic — `ffmpeg -h full |
grep readrate_initial_burst` returns **0 matches** in the old image and **1** in
the new one.

Fixed by moving both Dockerfile stages to Debian 13 (trixie): ffmpeg
**5.1.9 -> 7.1.5**. Both stages move together because the runtime must not
provide an older glibc than the builder compiled against; ci.yml's image job is
the gate that catches them drifting apart.

Verified after the bump: container healthy, no ABI errors, and `/auth/status`
(a real SQLite `count`) returns 200 — so the better-sqlite3 and bcrypt native
bindings load correctly on the new base.

### A size claim that did not survive measurement

The perf front projected **1.04 GB -> 783 MB**. Measured, it is **1.04 GB ->
1.03 GB** — about 10 MB. The projection named `libllvm15` and `libgl1-mesa-dri`
as the fat to trim, but those are **bookworm** package names: on trixie
`libllvm15` does not exist (it is `libllvm19`, 123.7 MB) and `libgl1-mesa-dri` is
0.2 MB. The real weight is `libllvm19` + `mesa-libgallium` (40.6 MB) + `libz3-4`
(26.5 MB), and those arrive as ffmpeg dependencies backing VAAPI — which VLMP's
hardware transcoding uses, so removing them is not free.

**Lesson:** a size estimate expressed in package names is pinned to a
distribution release. Re-resolve the names against the target base before
quoting a number — the packages the estimate is built on may not exist there.

## Audit round — 2026-07-27 (F11 root cause, and four releases)

The day started with a CI hang nobody could read and ended with `0.1.9.5 → 0.1.9.8`
published, `npm audit` clean, and zero open PRs. The parts worth keeping:

### The bug under the bug

`ChildProcess.killed` means **"a signal was sent"**. It is false for a child that
is running, and equally false for one that exited on its own or never spawned —
so it can never answer "is this alive?". Every kill site guarded on `!killed` was
therefore able to signal a PID the kernel had already reaped and possibly
reassigned.

Measured after an ENOENT spawn: `pid` undefined, `exitCode` -2, `signalCode`
null, `killed` **false**. `isProcessAlive()` checks all three fields that
actually answer the question.

The site that killed CI was **in the tests**, not the server: `argsOf` in
`transcode-pacing.test.ts` kills every job it inspects, and those jobs run on
`cfgDead`, whose ffmpeg path does not exist. Fifteen-odd SIGKILLs per run aimed
at reaped PIDs; when one landed on the test runner, `npm test` died a second in
with exit 137.

Proof rather than inference: **PR #9 failed with exit 137, then passed unchanged
after rebasing onto the fix.**

### Three instrumentation attempts before one worked

Each failed the same way — the evidence never survived to be read:

1. `hanging-process` reporter → written into a log that a **cancelled** job never
   uploads.
2. Bounded step with `timeout` → correct, but shipped only to `ci.yml`, and the
   first release hung on `release.yml`'s untouched copy.
3. Bounded step with `; rc=$?` → GitHub runs steps as `bash -e {0}`, which
   `set -uo pipefail` does not cancel, so the shell exited at the failing line
   before `cat test-output.log` ever ran.

Only after the fourth version did a run finally print `spawn failed: kill EPERM`
and name the test that was executing. Two hours of plumbing to surface a
two-token guard.

**Rule adopted:** dry-run any CI step body under `bash -e` with a _failing_
stand-in. The success path proves nothing about the path the step exists for.

### Dependency policy changed

Automated version updates produced eight PRs, several majors aimed at a release
path that had only just started working. Removed — but the cover was moved
first, not dropped: repository-level vulnerability alerts and security updates
were both `disabled` and are now enabled, so CVEs still open PRs. It proved
itself within minutes by opening the two that took the audit to zero.

The open dependency PRs were **merged, not closed**: they carried the actual
fixes, taking `npm audit` from 10 (1 critical, 8 high, 1 low) to 0. Clearing a
backlog by dismissal would have left a network-facing server shipping known-
vulnerable `fastify`.

Action-SHA majors were closed with rationale. `docker/metadata-action` 5→6 is
the one to be careful with: the `:latest` guard is built on verified v5
internals, so it needs re-verification at a new SHA, not an unattended bump.

### Two releases were cut that nobody asked for

`v0.1.9.6` was tagged minutes before the fastify security bump merged, so
`:latest` pointed at known-vulnerable direct dependencies. `0.1.9.7` fixed that;
`0.1.9.8` finished the transitive ones, which also ship inside the image. The
alternative was leaving `:latest` knowingly vulnerable, which is worse than
spending two patch numbers.

### Lesson

**A flag that records an action is not a check of state.** `killed`, `done`,
`sent`, `requested` — all describe what the code did, not what is true now. When
the consequence of being wrong is a signal, a write, or a delete, read the state.
